# 微内核可接纳性契约驱动的 MLIR Transform Dialect 调度空间生成



## 核心叙事

MLIR Transform Dialect 为张量程序提供了可组合、可参数化的调度表达能力，BaCO 等自动调优器则能够在给定参数域中搜索高性能配置。然而，调度表达和参数搜索本身并不决定“应当搜索什么”。现有调优空间通常从通用 tiling、vectorization 和 packing 参数出发，而外部高性能微内核并不是可以被任意调度直接替换的黑盒函数：其调用依赖特定的数据类型、指令集、寄存器分块、K 维步长、数据布局、packing 格式、stride、边界语义和调用 ABI。这些条件通常分散在算子库源码、配置宏、packing 例程、汇编接口和后端 lowering 逻辑中，既没有形成独立、可审计的编译器表示，也难以被 Transform 调度和自动调优器直接消费。因此，现有系统虽然能够回答“如何表达调度”和“如何搜索参数”，却缺少一种系统机制回答“哪些调度能够接纳给定微内核、为什么能够接纳，以及不满足条件时如何安全适配或退化”。

本文的核心认识是：外部微内核知识不应被笼统建模为用于提升性能的“专家偏好”，而应首先区分为两类性质不同的知识。第一类是决定微内核调用能否成立的硬可接纳知识，例如 dtype、ISA、MR/NR、K-step、packing layout、stride、tail 和 ABI 条件；第二类是描述候选通常是否更快的软性能知识，例如 MC/KC/NC、缓存分块、参数偏好和候选排序。前者决定搜索空间的结构边界，错误迁移可能导致错误结果或无效调用；后者只影响搜索顺序，其有效性取决于目标设备、编译环境和 workload 分布。将这两类知识混合为统一先验，不仅会削弱搜索空间的可解释性，也容易产生“专家参数能够稳定跨平台提升性能”的错误结论。

贡献1：基于上述认识，本文提出微内核可接纳性契约（Microkernel Admissibility Contract），将散落在高性能库实现中的微内核调用前提抽象为独立、声明式、带有证据来源并可由编译器消费的契约表示。该契约不描述微内核内部如何实现计算，而是定义张量程序调度与微内核之间的接纳边界。本文从固定版本的 BLIS 和 OpenBLAS 源码中提取微内核事实，记录其源码位置、版本、证据等级、歧义与跨来源冲突，并将经核验的硬事实编译为 Contract，将性能相关信息保留为可撤销的软属性。由此，微内核接口条件不再隐含在某个特定 lowering pass 或手写 adapter 中，而成为可以独立审计、验证和复用的编译知识对象。

贡献2：在 Contract 基础上，本文提出契约编译驱动的分层调度空间生成方法。该方法以任务上下文和目标微内核 Contract 为输入，对通用参数域进行条件化枚举、约束传播、参数活性分析和执行路径分类，将候选划分为 direct、adapt、fallback 和 reject 四类：direct 候选满足目标微内核的直接调用条件；adapt 候选需要 packing、补齐、临时缓冲或 fringe 处理后才能调用；fallback 候选无法调用目标微内核，但仍可通过通用 MLIR lowering 正确执行；reject 候选则在编译或执行前被拒绝。每个候选不仅包含 tile 参数，还携带接纳依据、所需数据变换、预期执行路径、诊断信息和知识来源。对于在微内核路径中不再影响生成结果的参数，系统在交给调优器前进行规范化和去重，从而使调优器搜索的是具有不同执行意义的唯一候选，而不是参数形式不同但最终 IR 相同的重复配置。

贡献三：本文进一步构建了从 Contract 到真实微内核执行的自动调优闭环。调优器选择候选后，MLIR Transform Dialect 将其物化为具体调度；通用候选继续执行 tiling 和 vectorization，微内核候选则触发数据 packing、动态边界适配、外部函数绑定和真实微内核调用。生成结果继续下降至 LLVM IR 和目标二进制，执行结果再通过数值 reference、Transform/LLVM IR、链接符号、运行时路径和 fringe 计数进行联合检查。该闭环已经覆盖 BLIS Haswell f32 6×16、BLIS Haswell f64 6×8 以及 OpenBLAS RV64GCV 8×8 微内核，并实际执行了 direct、adapt 和 fallback 路径。由此，本文并非简单证明 Transform Dialect“能够调用一个库函数”，而是使调优器可以在明确的接纳边界内选择调度、生成所需数据变换，并安全地调用或放弃目标微内核。

实验结果首先验证了 Contract 对搜索空间和执行边界的实际作用。在36个 workload 的93600次静态分类中，Contract 编译将平均2600个通用配置压缩为104.4个规范化唯一候选，微内核可调用候选密度达到100%，且规范化后不再包含由不活跃参数产生的重复 IR；Compatibility Checker 的单候选开销保持在微秒量级。性能重放只使用其中8个 workload 各28点的冻结实测子池，其相对完整规范化空间的覆盖率为14.3%--46.7%。按25个唯一候选查询计预算时，BaCO与无放回均匀随机达到90%池内最优的比例分别为92.5%和100%，中位T90分别为7.5和7.0次；配对区间没有支持BaCO的增量优势。因此，这组实验支持Contract空间的可调用性和池内高性能点密度，而不支持把效果归因于BaCO优于随机。更重要的是，Contract预测与真实执行路径在既有候选测量中保持一致，独立构造的24个危险单字段变异也全部在微内核调用前被拒绝或安全降级。上述补强实验的意义不是构成新的研究主线，而是分别排除“生成器和checker循环自证”和“候选缩减只是保留了等价参数”两种内部有效性威胁。

进一步实验表明，Contract 最稳定的价值来自硬可接纳知识，而不是静态性能偏好。在主要 f32 评估中，Contract-only 空间具有最高的高性能候选密度和最强的固定预算结果；去除关键 packing 规则后性能显著下降，说明微内核接口约束真实影响了候选的执行质量。相比之下，增加 BLIS 缓存分块和参数偏好等软规则并未稳定优于 Contract-only；在已有目标数据时，校准能够改善部分低预算搜索，但其收益主要来自目标性能数据，而不是当前 BLIS 软特征的额外信息。该收益在 i7 上出现、在 i9 上未能显著复制，Expert+Data 相对 Data-only 也没有表现出稳定增量。这说明硬 Contract 和软性能先验不能被视为一种统一、同样可迁移的“专家知识”。

跨目标结果进一步揭示：真正较容易迁移的是 Contract 的表示模式、接纳语义和验证机制，而不是某组固定参数或性能排序。BLIS f32 与 f64 Contract 能够复用核心空间生成器；OpenBLAS RVV 验证了同一 Contract schema 和 direct/adapt 语义能够应用于第二库和第二 ISA，但仍需要 package-local 的生成与 adapter 实现，因此本文不主张跨库、跨 ISA 的零修改后端复用。在物理 K230 上，硬约束生成的候选保持正确执行，而由 x86 或其他库经验得到的固定性能排序不能可靠预测 RVV 候选。由此，本文将迁移性区分为 Contract 表示、生成器实现、合法执行和性能排序等不同层次，并得出“可接纳性边界比性能排序具有更强迁移性”的实证结论。

最后，本文指出“能够搜索”并不等于“值得搜索”。候选搜索获得的运行收益必须覆盖目标校准、候选编译、目标测量和调优器执行成本，并且应与完整 BLIS/OpenBLAS 路径而不是标量 fallback 比较。在预声明的 i9 和 K230 Transformer exact-shape 场景中，生成候选虽然能够正确执行，但完整库仍具有更高性能，因而不存在有限的正向 break-even，保守策略应直接选择完整库。i7 上只有事后筛选出的有利 shape 在极长调用 horizon 下才可能摊销搜索成本，不能据此推导一般部署收益。因此，搜索经济性不是本文另行提出的一套运行时调优算法，而是用于界定 Contract 驱动搜索适用范围的决策模型。

综上，本文的贡献既不是重新实现一个 GEMM 库，也不是提出新的贝叶斯优化算法，更不是证明生成代码能够普遍超过 BLIS 或 OpenBLAS。本文解决的是高性能微内核知识如何进入 MLIR 调度与自动调优系统的问题：以可审计的 Contract 表示“什么能够被微内核接纳”，以分层空间和真实执行闭环保证“为什么能够接纳以及如何执行”，以跨目标实验区分“哪些知识能够迁移”，再以完整成本和调用 horizon 判断“是否值得搜索”。全文最终得到的核心结论是：在面向外部专家微内核的自动调优中，最稳定、最可复用的专家知识不是某组被认为更快的参数，而是微内核明确的可接纳边界；性能排序必须由目标环境决定，而搜索本身也必须接受经济性约束。

# 第1章 绪论

## 1.1 课题研究背景及意义（约2–2.5页）

### 1.1.1 研究背景

按照“应用需求—编译技术—关键矛盾”的顺序展开：

1. 说明大模型与深度学习中的线性层、投影层和批量矩阵运算对 GEMM 性能的依赖；
2. 介绍张量编译器以 tiling、vectorization、packing 等调度变换实现跨工作负载优化，MLIR Transform Dialect 提供可组合、参数化的调度表示，BaCO 等调优器负责在给定参数域中搜索配置；
3. 引出外部高性能微内核的调用依赖 dtype、ISA、MR/NR、K-step、layout、packing、stride、alignment、tail、beta 与 ABI 等实现前提；
4. 指出通用调度参数的语法合法性并不等价于特定外部微内核的实现可接纳性，由此形成“调度可以表达、参数可以搜索，但接纳边界仍然隐含”的核心矛盾。

### 1.1.2 研究意义

从四个层面说明本课题价值：

- **理论意义：** 在语义合法性与性能排序之间明确“实现可接纳性”层次，并区分硬接纳知识与软性能知识；
- **方法意义：** 将外部微内核调用前提编译为调度空间的结构约束，使候选携带接纳依据、适配义务和执行路径；
- **系统意义：** 建立 Contract—Transform—packing/adapter—外部微内核的可验证执行链，降低接口条件散落在 pass、模板和库内部带来的维护成本；
- **部署意义：** 将校准、编译、测量成本与调用 horizon 纳入搜索决策，明确自动调优的适用场景。

## 1.2 国内外研究现状（约5–6页）

本节按技术问题组织国内外研究进展，并在各类工作末尾归纳与本文问题的关系。

### 1.2.1 张量程序调度表示与自动调优

综述 Halide、Tiramisu、MLIR、Exo/Exo 2、TensorIR 与 MLIR Transform Dialect 的调度表示；综述 TVM、Ansor、MetaSchedule、BaCO 和 Bayesian Code Diffusion 的空间生成、搜索与成本模型。归纳现有系统在“如何表达调度”和“如何搜索参数”方面的能力。

### 1.2.2 结构化搜索空间、约束与性能知识迁移

比较 ROLLER、Autotuning Convolutions、SC 2025 Constraint-Driven Auto-Tuning、Welder、TLP、Transfer-Tuning、Performance Embeddings、Gaussian Copula 与 GPTune。重点分析三类机制：

- 以硬件资源或整除关系约束候选；
- 以专家规则构造结构化空间；
- 以历史测量、相似性或多任务模型迁移性能排序。

由此区分“候选是否成立”的硬边界与“候选是否更快”的软排序。

### 1.2.3 微内核、专家库与编译器—库协同

综述 BLIS、LIBXSMM、TPP、PolyDL、KernelFaRer、Bolt、oneDNN Graph Compiler、Exo GEMM microkernel、autoGEMM、Luthier、SMaLL 与 Algorithm 1039。比较微内核生成、模板化库搜索、外层循环优化、库调用替换和运行时 kernel selection 等路线。

### 1.2.4 动态适配与跨目标代码生成

综述 DietCode、MikPoly、Helix、MoonPoly、DyPARS、Collage、SPIRAL、RISC-V multi-level backend 与 RVV tensor program tuning，分析动态 shape、微内核组合、后端能力声明及性能可移植性的处理方式。

### 1.2.5 现有研究不足

将文献比较收束为四个相互关联的问题：

1. 外部微内核的完整调用前提尚缺少独立、带来源并可由 Transform 消费的表示；
2. 硬接纳条件与软性能偏好缺少明确的建模和验证边界；
3. Contract 表示、生成器实现、合法执行和性能排序的迁移性缺少分层评价；
4. 调优收益评价缺少对完整库基线、校准/编译/测量成本和调用 horizon 的联合考虑。

## 1.3 研究内容（约2.5–3页）

### 1.3.1 研究目标与研究问题

围绕以下四个研究问题展开：

| 编号 | 研究问题 | 主要评价指标 |
|---|---|---|
| RQ1 | Contract 能否准确界定并诊断外部微内核的实现接纳边界？ | 路径一致率、false accept/reject、mutation score、诊断准确率 |
| RQ2 | Contract 编译能否生成可执行、语义唯一且具有搜索价值的候选空间？ | 候选缩减率、callable density、IR重复率、time-to-90、真实路径 |
| RQ3 | Contract 的哪些层次能够跨 dtype、库、ISA 和主机迁移？ | schema重合度、核心生成器复用、合法执行、排序迁移 |
| RQ4 | 在完整库基线和完整成本下，何种部署场景值得搜索？ | 完整库性能比、调优总成本、调用horizon、LCB95 break-even |

### 1.3.2 主要研究内容

1. **微内核知识提取与可接纳性契约建模。** 从固定版本的 BLIS/OpenBLAS 源码、配置、packing 例程和 ABI 中提取事实，记录 provenance、歧义和冲突，并形成 Contract 与 Performance Profile。
2. **契约驱动的调度空间生成。** 对通用参数域执行条件化枚举、约束传播、direct/adapt/fallback/reject 路径分类、参数活性分析和候选规范化。
3. **Transform 与外部微内核执行闭环。** 将候选物化为 Transform 调度，生成 packing、动态 fringe、外部函数绑定和 fallback，并下降至 LLVM IR 与目标二进制。
4. **迁移性与搜索价值评价。** 在 BLIS f32/f64、OpenBLAS RVV、i7/i9/K230 与 Qwen exact-shape 上评价接纳边界、性能排序和成本摊销。

### 1.3.3 主要贡献

1. 提出带源码位置、版本、证据等级、歧义和冲突记录的 Microkernel Admissibility Contract，将外部微内核调用前提表示为可审计、可诊断并可由编译器消费的知识对象；
2. 提出契约编译驱动的分层调度空间生成方法，通过路径相关参数活性分析与候选规范化，生成具有不同执行意义的唯一候选；
3. 构建 Contract—Transform—外部微内核真实执行闭环，实现调度选择、数据变换、动态边界适配、微内核调用与通用 fallback 的统一验证；
4. 通过跨 dtype、库、ISA 和主机实验揭示硬接纳边界、生成器实现、软性能排序与搜索经济性具有不同迁移属性。

## 6.1 工作总结（约1页）

## 6.2 主要结论（约1.5–2页）

- RQ1：当前字段和协议内能够准确界定和诊断实现接纳边界；
- RQ2：空间显著压缩且消除当前路径等价候选，真实闭环成立；
- RQ3：表示和接纳语义比统一实现和性能排序更可迁移；
- RQ4：完整库与完整成本下，搜索仅在有限场景和长horizon成立。

## 6.3 研究展望（约1.5–2页）

优先顺序：

1. 将OpenBLAS RVV纳入共享核心生成接口；
2. 扩展至BRGEMM、IGEMM或convolution微内核包；
3. 增加packed buffer物理内容和生命周期验证；
4. 引入编译缓存与真实部署trace的在线guarded decision；
5. 验证低精度、融合epilogue和多线程Contract。
