# 硕士学位论文审稿意见

**论文题目**：微内核可接纳性契约驱动的 MLIR Transform Dialect 调度空间生成
**学科专业**：计算机技术（西北工业大学计算机学院）
**审阅日期**：2026 年 8 月 13 日
**审阅方式**：全文通读（96 页，6 章 + 参考文献 + 附录 A）

## 一、论文概要

本文研究张量程序自动调优中一个被忽视的接口问题：**一个语法合法、语义正确的 MLIR Transform 调度，在什么条件下可以安全调用外部高性能微内核（如 BLIS/OpenBLAS 中的寄存器级 GEMM kernel）**。论文的核心立场是将相关知识二分：

- **硬可接纳知识**（dtype、ISA、MR/NR、K-step、panel 布局、stride、tail、ABI 等）——违反将导致错误调用或错误结果，组织为"微内核可接纳性契约"（Microkernel Admissibility Contract, Contract）；
- **软性能知识**（MC/KC/NC 缓存分块、来源平台参数偏好等）——只影响候选排序，保留为带来源、可校准、可撤销的 Performance Profile。

围绕该立场，论文完成了四项工作：(1) 从固定 revision 的 BLIS 与 OpenBLAS 源码中提取带 provenance 的字段级 Fact，编译为 Contract；(2) 契约驱动的调度空间生成，产出 direct/adapt/fallback/reject 四类路径，并通过参数活性分析与 canonical key 消除语义重复候选；(3) 打通 Contract → Transform 物化 → packing/fringe 适配 → LLVM lowering → 真实微内核执行的完整链路，覆盖 BLIS Haswell f32 6×16、f64 6×8 与 OpenBLAS RV64GCV f32 8×8 三个微内核包（含 K230 RISC-V 物理开发板）；(4) 按 L1 语义合法性 / L2 实现可接纳性 / L3 性能经济性三层框架进行实验评价，并如实报告了大量负结果。

## 二、总体评价

**这是一篇工程质量高、方法论严谨、学术诚实度罕见的优秀硕士学位论文。**

论文最突出的品质不是某个单项指标，而是**证据纪律**：全文始终坚持"能证明什么就主张什么"，明确区分静态分类、manifest 重放、冻结语料离线重放与物理机实测四种证据强度；如实报告了跨主机校准复制失败（预注册判定 FAIL）、生成路径 0/10 工作负载不敌完整库、不存在有限正向盈亏平衡点等对核心叙事"不利"的结论，并将这些负结果升华为论文的真正论点——**可接纳性边界的表示与执行语义比性能排序更易复用，搜索是否值得发生必须由完整库基线与全成本共同裁决**。在"性能提升 X%"导向的系统领域写作中，这种克制尤为可贵。

论文的主要贡献属于**方法论与知识表示层面**：Contract 提供了一种可审计、可诊断、可由编译器消费的微内核接纳边界表示，L1/L2/L3 三层框架与"硬/软知识分离"原则对自动调优系统的知识工程具有一般性启示。其实用工具价值则受实验结论限制（生成路径未超过完整库），论文对此的表述是恰当的。

**审稿结论：同意答辩，建议评定为优秀硕士学位论文。** 以下意见供修改完善参考。

## 三、主要优点

1. **问题定位精准且真实**。"调度合法 ≠ 微内核可调用"是 MLIR/TVM 类系统接入专家库时的真实痛点，现有综述部分（1.2 节）按技术问题而非软件系统罗列相关工作，分析深入，表 1-1 的能力比较（尽管有自我评价偏差，见后文）明确了本文的问题组合边界。

2. **硬/软知识分离的建模原则有普适价值**。式 (3-1) 按"失败后果"而非"证据强度"分类字段——"证据强不等于约束硬"（3.2.2 节 MC=168 的例子）——这一区分直击调优系统把库内参数一锅端为"专家先验"的常见错误。

3. **实现闭环完整、验证手段立体**。从 Contract 编译、Transform 物化、packing、动态 fringe 适配到 LLVM/链接符号/运行时路径/数值 reference 的联合验证（式 4-13），且明确"任何单项证据不能替代其余证据"，工程严谨性远高于同类论文的常见水准。三个微内核包覆盖两个库、两种 ISA、两种 dtype，并含 K230 物理板实测。

4. **实验方法论规范**。预注册验收条件、冻结协议、design/validation/holdout 划分、workload-cluster bootstrap、右删失处理、对"事后选择"场景的明确标注（i7 的 19-shape 上界），均达到或超过系统领域会议论文的评审标准。5.6 节有效性威胁的写法（内部/构念/统计/外部四类）是实证软件工程的规范做法。

5. **写作结构清晰，边界声明贯穿全文**。几乎每一章末尾都显式陈述"本结果支持什么、不支持什么"，摘要即给出全部关键数字与限制条件，读者不会产生夸大预期。

## 四、主要问题与修改建议（Major）

### M1. 与经典概念的关系讨论不足，新颖性定位需加固

Contract 本质上是**外部实现的接口前置条件 + 能力声明 + 证据溯源**的形式化。论文未讨论它与若干经典概念的关系：

- **Design by Contract**（前置/后置条件）与本文"契约"的术语渊源——本文契约描述的是"调用方义务"而非被调方行为，术语选择容易引起歧义，建议增加一段辨析；
- **Feature model / capability-based dispatch**（如 BLIS 自身的 context 分派、Linux 内核的 capability 检查、Soname/ABI 版本机制）——这些机制同样表达"目标能否接纳某实现"，本文与它们的区别是"面向编译器候选生成的字段级可诊断表示"，这一差异值得显式论证；
- **TVM 的 target kind / TensorIR 的 tensorize 原语匹配**——2.1 节提到 TensorIR 但未展开对比其内禀匹配与本文接纳检查的差别。

**建议**：在第 1.2 或 2.x 节增加半页"与相邻概念的关系"，说明 Contract 的新颖性在于"带来源证据、字段级诊断、与调度空间编译器耦合"，而非契约思想本身。

### M2. 迁移性结论（RQ3）的证据面偏窄

三个微内核包中，BLIS f32 与 f64 同库同 ISA 同后端，真正独立的迁移证据只有 OpenBLAS RVV 一个包；且该包的候选生成器仍是 package-local（表 5-6 已如实说明）。Schema IoU=0.912 的数字建立在仅 3 个包、34 个叶路径的基数上，统计意义有限。i7→i9 的"同包跨主机"复制失败也只有两台机器各一次实验。

论文对边界的表述已经足够克制（"现有证据不能支持任意微内核包零修改接入"），作为硕士论文可以接受。**建议**在 6.3 局限性中进一步点明：IoU 等指标的分母过小，迁移性结论应理解为"存在性证明"而非比例估计；并将"接入第三个调用组织方式不同的库（如 BLASFEO 或 LIBXSMM 风格的运行时生成库）"在 6.4.1 中提升为验证 Schema 完备性的关键步骤而非可选项。

### M3. 缺少随机搜索基线，BaCO 的增量价值无法分离

5.3.3 节的离线重放显示 D90=0.1875、中位 time-to-90% 为 8 次查询。但在 28 候选的冻结池上，**均匀随机采样抽到 top-18.75% 候选的期望等待时间约为 1/0.1875 ≈ 5.3 次**——BaCO 的 8 次中位数与随机搜索的关系并未给出。B1（通用空间上的 BaCO）是空间对照而非搜索算法对照。这削弱了"搜索有价值"论证中算法一侧的归因。

**建议**：补充同一冻结池上的 random search（含重复去重口径）重放对照，或在文中显式说明本实验只评价"空间结构 + 搜索器组合"，不分离搜索器贡献。若 BaCO 未显著优于随机，应如实写出——这与全文的诚实风格一致，且不影响 RQ2 关于空间结构的主要结论。

### M4. C 空间规模（104.4）与实测池规模（28）之间的衔接不透明

表 5-4 的规范化 C 空间平均每工作负载 104.4 个候选，而 5.1.3 与 5.3.3 节的冻结实测池每工作负载最多 28 个候选，D90/T90 等全部性能指标均基于 28 候选池。104.4 → 28 的子采样策略（如何选、是否固定、是否引入选择偏差）在正文中不够醒目，5.3.3 节"折叠与回填协议"一段对非实现读者而言偏晦涩。由于全部"搜索价值"数字都建立在这个 28 候选池上，该环节的透明度直接影响 RQ2 的说服力。

**建议**：在 5.1.3 或 5.3.3 增加一小节明确说明：(a) 28 个候选的选取规则与冻结时间；(b) 池内 direct/adapt 比例相对 C 空间的代表性；(c) 若存在预算驱动的选择，分析其对 D90 的潜在影响。

### M5. 与 MLIR 上游生态的关系未讨论

transform.buddy.call_microkernel 是 buddy-mlir 中的自定义 Transform op。论文未说明：(a) 该设计为何不能由 MLIR 现有的 transform 外部调用机制（如 transform.apply_registered_pass 直接替换 callee、或 transform.structured 系列）表达；(b) Contract 驱动的空间生成器是否可能/值得上游化，或以独立工具形式与 MLIR 版本解耦。考虑到 buddy-mlir 与 LLVM/MLIR 的快速演进，这关系到工作的可复用性。

**建议**：在 4.5.1 后增加一段讨论，并在 6.4 后续工作中说明与上游同步的策略。

## 五、次要问题（Minor）

1. **表 1-1 的自我评价偏差**。"本文"一行全部标记"直接"，容易被质疑为立靶自射。建议改为按"本文证据覆盖"标注，或在表注中重申该表仅界定问题组合。
2. **符号体系冗余**。式 (2-8) 与式 (5-2) 分别用吞吐率比和时间比定义 D90，语义重复；式 (2-11) 与式 (5-3) 同样重复出现。建议第 5 章直接引用第 2 章定义。
3. **checker 的形式化程度**。式 (3-4) 的谓词合取只是声明语义，论文承认"经验验证不是对所有输入的形式证明"（4.7 节）。建议至少明确陈述 checker 相对于 Contract 语义的 soundness/completeness 含义（例如：checker 完备地枚举声明字段，但对 packed buffer 内容不 sound），避免读者过度解读。
4. **WSL2 实验环境**。i7 正式实验在 WSL2 上进行（5.1.2 节），虽经绑核与资格审计，仍是可避免的威胁。建议后续工作将全部正式测量迁回原生 Linux，并在文中解释 i7/WSL2 与 i9/原生两套环境并存的历史原因。
5. **中英文混排**。PDF 中英文术语在行尾断行后空格丢失现象较多（如 "MicrokernelAdmissibilityContract""TransformDialect" 连写），建议检查 LaTeX 的 xeCJK/断词设置，统一中英文之间空 grp 的处理。
6. **附录偏薄**。附录 A 仅有工作负载表。建议增加：(a) Contract 完整 Schema 字段清单（正文代码清单 3-1 为精简版）；(b) 稳定 reason code 列表（4.2.4 节提到 PACKING_REQUIRED 等）；(c) artifact 获取方式与复现指南链接——论文已有 manifest + SHA-256 审计的良好基础，补上 artifact 可用性声明即可显著提升可复现性评价。
7. **图 4-3 的示例代表性**。sq_096 的单个别名对示例已声明"不表示总体缩减比例"，建议补充一张跨工作负载的规范化前后候选数分布图，使该规则的作用幅度可见。
8. **个别表述**。6.2.4 标题"能够搜索不等于值得搜索"很好；摘要中"上述结论限于受测的行主序、单线程 rank-2 GEMM 和三个微内核包"位置靠前且完整，值得肯定，无需改动。

## 六、对几个可能质疑点的回应（供答辩参考）

| 质疑 | 本审稿人看法 |
|---|---|
| "生成代码不如完整库，方法有什么用？" | 论文的价值主张本就不是替代完整库，而是让接入过程可审计、可诊断、可决策；RQ4 的负结果恰恰是方法论成立的证据（能判定"不该搜索"本身即收益）。 |
| "只有 GEMM、单线程、rank-2，范围太窄" | 范围声明充分，且 fringe/动态 shape 已覆盖；窄范围内的深证据优于宽范围内的浅证据。 |
| "Contract 是否只是配置文件？" | 区别在于字段级 provenance、证据等级、冲突/失效管理与 checker 诊断接口的耦合；但论文应主动回应此问（见 M1）。 |
